1) Relation R1(L,M,N,O,P,Q,R,S), S1 = { L->NQ, MNR->O, O->M, NQ->LS, S->OPR }

(a) BCNF violations

- L is a superkey since L+ = all attributes.
- NQ is a superkey since NQ+ = all attributes.
- O is not a superkey (O+ = OM).
- S is not a superkey (S+ = SOPR).
- MNR is not a superkey (MNR+ = MNRO).
Violations: MNR->O, O->M, S->OPR.

(b) BCNF decomposition
Start with R1(LMNOPQRS).
Use O->M:

- R11(OM)
- R12(LNOPQRS)
In R12, S->OPR still violates BCNF. Decompose:
- R121(OPRS)
- R122(LNQS)
Final BCNF relations (alphabetical):
- LNQS
- MO
- OPRS
Projected FDs:
- On LNQS: L->NQ, NQ->LS
- On MO: O->M
- On OPRS: S->OPR

(c) Dependency preservation
Not dependency-preserving.
MNR->O is not present in any single final relation and is not derivable from
projected dependencies over LNQS, MO, and OPRS.

(d) Chase test (lossless)
Rows for MO, OPRS, LNQS are initialized in the chase tableau.
Because intersection attributes determine one side at each decomposition step:

- In R1 -> MO and LNOPQRS, intersection is O, and O->MO holds.
- In LNOPQRS -> OPRS and LNQS, intersection is S, and S->OPRS holds.
Applying S->OPR and then O->M to the LNQS row eventually gives distinguished
symbols for all attributes. Therefore the decomposition is lossless.

2) Relation R2(A,B,C,D,E,F,G,H),
S2 = { AB->C, C->ABD, CFD->E, E->B, BF->EC, B->DA }

(a) Minimal basis
After splitting and minimizing:

- AB->C becomes B->C (A is extraneous because B->A).
- C->A and C->D are redundant (C->B and B->A,D).
- BF->C is redundant (B->C).
- CFD->E is redundant (C->B and BF->E).
A minimal basis (alphabetical) is:
- B->A
- B->C
- B->D
- BF->E


## - C->B

## - E->B

(b) All keys for R
Attributes not on RHS are F,G,H, so every key must include FGH.
Adding one of {B, C, E} yields all attributes:

- BFGH
- CFGH
- EFGH
These are all candidate keys.

(c) 3NF synthesis
Combine same LHS:

- B->ACD
- BF->E
- C->B
- E->B
Create relations:
- R1(ABCD)
- R2(BEF)
- R3(BC)
- R4(BE)
Remove subset relations:
- BC is subset of ABCD, remove BC.
- BE is subset of BEF, remove BE.
No relation contains a key for R2, so add one key relation, e.g. BFGH.
Final 3NF decomposition:
- ABCD
- BEF
- BFGH

(d) Redundancy
Yes, redundancy can still exist in this 3NF design.
In relation BEF, projected dependency E->B has non-superkey LHS E.
So repeated B values can occur for the same E across multiple F values.
